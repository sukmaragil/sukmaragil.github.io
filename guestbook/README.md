# Standalone guestbook — Supabase setup

One self-contained file: `index.html`. No build step, no dependencies. Opened locally it runs in browser-only mode; connected to Supabase it becomes a shared wall.

**No keys live in this file.** The config block holds placeholders:

```js
window.GUESTBOOK_CONFIG = {
  supabaseUrl:  "__SUPABASE_URL__",
  supabaseKey:  "__SUPABASE_ANON_KEY__",
  table:        "__SUPABASE_TABLE__",
  openFeedback: "__OPEN_FEEDBACK__",
  homeUrl:      "__HOME_URL__"
};
```

They are substituted at deploy time by the site's `.github/workflows/deploy.yml`. Any placeholder left unreplaced is treated as empty, so the page falls back to browser-only mode instead of breaking.

Total setup time: **about 15 minutes**, most of it waiting for the project to provision.

---

# Step 1 — Create the Supabase project

1. Go to **supabase.com** → **Start your project** → sign in with GitHub.
2. **New project**, inside your personal organization.
3. **Name:** `guestbook` (only you see this).
4. **Database password:** click Generate, then **save it in your password manager**. You will not need it for this setup, but it cannot be retrieved later — only reset.
5. **Region: Southeast Asia (Singapore)** — closest to Jakarta. This is the one choice you can't change later without recreating the project.
6. **Plan:** Free.
7. Click **Create new project** and wait ~2 minutes for provisioning to finish.

# Step 2 — Create the table

Left sidebar → **SQL Editor** → **New query**. Paste this entire block and click **Run** (or Ctrl/Cmd + Enter):

```sql
create table guestbook (
  id bigint generated by default as identity primary key,
  name text not null default 'anonymous',
  message text not null,
  color text not null default '#fff3bf',
  created_at timestamptz not null default now()
);

alter table guestbook enable row level security;

create policy "public read" on guestbook
  for select using (true);

create policy "public insert" on guestbook
  for insert with check (
    char_length(message) between 1 and 240
    and char_length(name) <= 32
  );
```

**Expected result:** `Success. No rows returned.` That is correct — the statements create rather than return.

What you just did, line by line:

| Statement | Effect |
|---|---|
| `create table` | The notes table: id, name, message, color, timestamp |
| `enable row level security` | Denies everything by default — without this the anon key could read and write freely |
| `public read` policy | Anyone may read notes |
| `public insert` policy | Anyone may post one, but only if it passes the length checks |

No update or delete policy exists, so **nobody can edit or delete a note from the browser** — including you. Deletion happens in the dashboard.

**Verify it:** sidebar → **Table Editor** → you should see `guestbook` with columns and zero rows. If the table is missing, the SQL didn't run — re-check for an error message in the editor.

# Step 3 — Copy your two keys

Sidebar → **Project Settings** (gear icon) → **API**.

| What to copy | Where | Looks like |
|---|---|---|
| **Project URL** | top of the page | `https://abcdefgh.supabase.co` |
| **anon public** key | Project API keys | `eyJhbGci...` (very long) |

⚠️ **Never copy the `service_role` key.** It bypasses every policy you just wrote. It belongs only on a server, never in a webpage or a repo.

# Step 4 — Store the keys in GitHub

In your site repo: **Settings → Environments → `github-pages`** (click **New environment** and name it exactly that if it doesn't exist).

**Environment secrets** → **Add secret**, twice:

| Secret name | Value |
|---|---|
| `SUPABASE_URL` | the Project URL from step 3 |
| `SUPABASE_ANON_KEY` | the anon public key from step 3 |

**Environment variables** → optional, add only if you want to change a default:

| Variable | Value | Default |
|---|---|---|
| `OPEN_FEEDBACK` | `true` or `false` | `true` |
| `SUPABASE_TABLE` | table name | `guestbook` |
| `HOME_URL` | where "← Back to site" points (`""` removes it) | the site's own `baseurl` |

Names must match exactly — the workflow reads them by name, and a typo deploys silently in browser-only mode.

**Why the environment and not the repo:** only the deploy job can read these, and you get an audit trail of which deployments used them.

**What this does and doesn't buy you.** The anon key still appears in the *deployed* HTML. That's unavoidable for any browser-side database and is exactly what that key is designed for — your row-level policies are the real protection. What you gain is nothing sensitive in the repo, no key in clones or forks, and rotation without a commit.

# Step 5 — Deploy

The guestbook is published by the **main site's** workflow, `jekyll-site/.github/workflows/deploy.yml`. It builds the Jekyll site, injects your keys into this page, and publishes it at **`/guestbook/`** on the same Pages site.

**Repo layout it expects:**

```
your-repo/
├── .github/workflows/deploy.yml     from jekyll-site/
├── _config.yml, index.html, _posts/ …
└── guestbook/
    └── index.html                   this page → /guestbook/
```

1. Confirm **Settings → Pages → Source** is set to **GitHub Actions**.
2. Push to `main` — or **Actions → Deploy site → Run workflow** to trigger it by hand.
3. Watch the run under the **Actions** tab. In the **Add standalone guestbook** step you should see `guestbook config injected`.

There is deliberately only one workflow that deploys to Pages: a repo has exactly one Pages site, so a second deploying workflow would overwrite whatever the first published.

If `guestbook/index.html` isn't present the step is skipped and the site deploys without it.

# Step 6 — Verify it actually works

1. Open `https://<your-site>/guestbook/`.
2. The blue **"Not connected yet"** notice must be **gone**. If it's still there, the keys didn't reach the page — see troubleshooting.
3. Post a test note.
4. In Supabase → **Table Editor → guestbook**, your note should be a row.
5. Open the page in a private window. The note should be visible there too — that's the real proof it's shared rather than local.

Then delete the test row from the Table Editor.

# Troubleshooting

Open the browser console (F12) on the guestbook page and post a note; the failing request tells you which case you're in.

**Still shows "Not connected yet"**
The placeholders weren't substituted. Check the Actions log for the warning `SUPABASE_URL / SUPABASE_ANON_KEY environment secrets not set`. Usual causes: secrets added to the repo instead of the `github-pages` environment, a misspelled name, or the environment named something other than `github-pages`.

**401 or 403 on the POST**
Row-level security is on but the insert policy is missing or didn't apply. Re-run the `create policy` statements from step 2. Also check your note is under 240 characters — the database enforces that independently of the page.

**404 on either request**
The table name doesn't match. Default is `guestbook`; if you named it differently, set the `SUPABASE_TABLE` variable to match.

**Notes load but posting silently fails**
Almost always the 30-second client cooldown between posts, or a URL in the message (blocked as spam). The status pill above the input bar says which.

**Everything works, then stops after a week**
Free-tier projects pause after 7 days with zero activity. Wake it from the dashboard. Any real traffic prevents this.

# Running it

## Turning posting off

Set the `OPEN_FEEDBACK` environment variable to `false` and re-run the workflow — or pick `false` from the **Run workflow** dropdown for a one-off. The input bar isn't rendered at all; existing notes stay readable.

## Moderating

Notes publish instantly. The page blocks empty and over-length notes, URLs, and rapid repeat posting; the database enforces the length caps independently. To remove a note: **Table Editor → guestbook** → select the row → delete.

## Rotating the anon key

Supabase → **Project Settings → API → Rotate**. Update the `SUPABASE_ANON_KEY` secret, re-run the workflow. No commit needed.

## Backing up

**Table Editor → guestbook → Export → CSV.** Worth doing occasionally; the free tier has no point-in-time recovery.

# Alternatives

## Hosting the page on Supabase instead of GitHub Pages

Supabase has no static-site product, so you'd serve the file from **Storage**. This route has no CI, so you must paste the keys into the file by hand before uploading — which puts them back in your working copy.

1. **Storage → New bucket** → name `site` → tick **Public bucket** → create.
2. Upload `index.html`.
3. Open the file → **Copy URL** → `https://<project>.supabase.co/storage/v1/object/public/site/index.html`

Re-uploading the same filename replaces it. Storage sets a cache header, so allow a few minutes or hard-refresh.

**Worth knowing:** that URL is long, not brandable, and Storage won't map `/` to `index.html`. Fine for sharing a link; poor if visitors will type the address.

## Keeping the guestbook in its own repo

Don't reuse the site workflow as-is — it's written for the layout above. Either copy just the "Add standalone guestbook" step into a workflow whose `SRC` points at the real path, or use **Cloudflare Pages / Netlify** (create a project from the repo, output directory `/`, add a build step that substitutes the placeholders from environment variables). The Supabase side is identical either way.

## Keeping it in sync with the main site

This page is a standalone copy — it shares no files with `jekyll-site/`. Restyling one won't change the other. That's the tradeoff for it being a single portable file.
